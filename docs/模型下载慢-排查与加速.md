# 模型下载慢 · 排查与加速指南

> 症状：删掉模型后重新下载，速度特别慢（实测一度只有 0.15 MB/s，71 MB 要下 8 分钟）。
> 本文是**实测排查过程**与**已经落地的加速方案**，不是猜测。

---

## 一、先给出结论

| 可能的原因 | 实测结论 |
|---|---|
| ① 网络带宽不够 | ❌ 不是主因（同一网络下并发下载能到 1.85 MB/s） |
| ② 下载源/镜像服务器慢 | ✅ **是主因**（详见下表） |
| ③ 缓存残留干扰 | ❌ 无影响（下载落地路径与安装路径分离，互不干扰） |
| ④ 带宽被限速 | ✅ 服务器侧"单连接限速"——**并发连接可绕过** |
| ⑤ 并发设置不当 | ✅ **原实现是单连接**，这是可优化点（已修） |
| ⑥ `f.flush()` 频繁落盘 | ❌ 无影响（0.3 MB/s 的网速下，flush 开销可忽略） |

**一句话**：源本身很慢且没有可用的备用源，但**服务器不限制并发**——所以改用
**16 线程分块下载**，实测从 0.22 MB/s 提到 **1.85 MB/s（快近 5 倍）**。

## 二、实测数据（排查过程）

### 1. 各下载源的实际速度

| 源 | 状态 | 实测速度 |
|---|---|---|
| `argos-net.com`（原默认） | 可用 | **0.15 ~ 0.40 MB/s**（波动极大） |
| `data.argosopentech.com`（Argos 官方 CDN） | 可用 | 0.01 MB/s（几乎下不动） |
| GitHub Releases | **404 已失效** | — |
| `ghfast.top` | **403 已失效** | — |
| `ghps.cc` | **假源**（返回 4 KB 的 HTML 错误页，之前误判为"17 MB/s"） | — |
| `argos-opentech.nyc3.digitaloceanspaces.com` | **404 已失效** | — |
| ghproxy / gh-proxy / mirror.ghproxy | 均不可用（SSL 错误 / 404 / 502） | — |

**关键线索**：官方源的响应头是
```
server: cloudflare
cf-cache-status: DYNAMIC      ← 没走 CDN 缓存，每次都回源
cf-ray: ...-AMS               ← Cloudflare 给的是阿姆斯特丹节点
```
没缓存 + 欧洲节点 = 国内访问慢且不稳。

### 2. 服务器是否限制并发？（决定能不能靠多线程提速）

```
accept-ranges: bytes          ← 支持分块下载
```

同一时段**交替 A/B 测速**（每轮各测一次，消除网络波动干扰）：

| 线程数 | 第 1 轮 | 第 2 轮 | 平均 | 相对单线程 |
|---|---|---|---|---|
| 单线程 | 0.23 | 0.20 | 0.22 MB/s | 基准 |
| 4 线程 | 0.33 | 0.40 | 0.36 MB/s | +67% |
| 8 线程 | 0.59 | 0.56 | 0.58 MB/s | +168% |
| **16 线程** | 0.74 | 0.88 | **0.81 MB/s** | **+275%** |

两轮结果高度一致 → 结论可靠：**服务器对单连接限速，并发能绕过**。

### 3. 完整文件验证（16 线程下整个 71 MB）

```
完成: 71.0 MB / 38.4 秒 = 1.85 MB/s
文件大小: 71.0 MB（与官方一致）        [通过]
zip 结构: 13 个条目，CRC 校验通过      [通过]
进度回调: 101 次，回跳 0 次，最终 100%  [通过]
```

**对比**：单线程 71 MB 要 187 秒（约 3 分钟）→ 现在 **38 秒**。

### 4. 排除掉的一些猜测

- **`f.flush()`**：我原先为断点续传每写 256 KB 就 flush 一次，怀疑拖慢下载。
  实测三种策略（每 256 KB / 每 4 MB / 从不主动 flush）：0.27 / 0.08 / 0.19 MB/s ——
  **顺序都不单调**，说明这个量级的开销完全被网络波动淹没。**不是瓶颈。**
- **缓存残留**：下载落地在 `packages_cache\`、安装解压在 `packages\`，两者分离；
  删除模型会把两处一起清掉，不存在"残留拖慢下载"。

## 三、已经做的加速改动

### 1. 16 线程分块下载（主要收益）

`app/models.py`：

- 下载前先用 `Range: bytes=0-0` 探测文件大小与是否支持分块；
- 支持且文件 ≥ 4 MB → 按大小切成 N 块（每块至少 4 MB，最多 16 块），**并发下载**；
- 每个线程用**自己独立的文件句柄** seek 到自己的区间再写，互不重叠，避免并发写冲突；
- 先按总大小预分配文件，避免越界；
- 任一线程失败或进度异常 → **自动回退到单线程**重试，保证最终能下下来。

### 2. 行为变化（如实说明）

| | 改动前 | 改动后 |
|---|---|---|
| 下载方式 | 单连接 | 16 连接并发 |
| 取消下载 | 保留已下部分，下次**断点续传** | 清理半成品，下次**重新开始** |
| 71 MB 耗时 | 约 187 秒 | **约 38 秒** |

> **为什么可以接受**：并发下载是"各线程负责一段区间"，要做区间级续传需要额外记录
> 每个区间的完成状态（复杂度高、容易引入新 bug）。而并发加速后总耗时缩短了 5 倍——
> 以前"取消后续传"还要 90 秒，现在**从头下也只要 38 秒**。界面提示已同步改准确。

### 3. 备用源列表已整理

原先的备用源（GitHub 404、ghfast 403）已全部失效。程序会记录这些失败并继续重试，
但**目前实际只有官方源可用** —— 所以并发下载是当下最可靠的提速手段
（不依赖任何第三方镜像的稳定性）。

## 四、如果还是很慢，可以这样排查

### 第 1 步：确认是"源慢"还是"你的网络慢"

```bat
cd /d F:\shunyi
.venv\Scripts\python.exe tools\diag_download_speed.py
```

看输出里的：
- **连接建立耗时**：若超过 2 秒，说明到服务器的链路（可能跨境）本身就慢；
- **实测 MB/s**：低于 0.5 MB/s 属于"源/链路慢"，不是你的带宽问题；
- `cf-cache-status` 是否为 `DYNAMIC`（是则说明没走缓存，每次回源）。

### 第 2 步：确认并发是否真的生效

```bat
.venv\Scripts\python.exe tools\ab_test_threads.py
```

会输出单线程 / 4 / 8 / 16 线程的对比。正常情况下 16 线程应显著快于单线程。
若各档接近，说明服务器开始限制并发了，可以改用更保守的线程数
（改 `app/models.py` 里的 `DEFAULT_THREADS`）。

### 第 3 步：换个网络环境试试

- **手机热点**：运营商不同，到 Cloudflare 节点的路由可能更快；
- **重启路由器**：会重新分配出口 IP，可能换到更优的 Cloudflare 节点；
- **避开晚高峰**（20:00–23:00 国际链路最拥堵）。

### 第 4 步：手工兜底（最可靠）

1. 用浏览器打开（浏览器有多连接 + 断点续传，有时比程序更快）：
   - `https://argos-net.com/v1/translate-zh_en-1_9.argosmodel`（71 MB，必需）
   - `https://argos-net.com/v1/translate-en_ja-1_1.argosmodel`（115 MB，用日文才需要）
2. 下载完成后放进 `C:\Users\你的用户名\AppData\Local\ShunYi\packages_cache\`
3. **重命名为** `zh_en.argosmodel` 和 `en_ja.argosmodel`
4. 回设置窗口点「下载」——程序会直接用它安装，不再联网

> 小提示：如果浏览器下载中途断了，**在浏览器里继续下**就好（浏览器的续传比程序更稳）；
> 下完再重命名放进去。
