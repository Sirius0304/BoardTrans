# 常见问题与排障手册

> 遇到问题先做这件事：**双击 `0-自检.bat`**。
> 它会逐项体检并给出中文结论，下面几类问题它都能直接定位。

---

## 零、设置界面相关问题（新增功能）

### 点「设置…」弹出"需要 tkinter 图形库"

**窗口内容**：

```
设置界面需要用到 Python 自带的 tkinter 图形库，但这个 Python 环境里没有。
常见原因：装的是精简版 Python（例如某些绿色版/嵌入式版）。
...
```

**原因**：你的 Python 是精简版，没有自带图形库。**翻译功能完全不受影响**。

**解决（二选一）**：

1. 换官方完整版 Python 重建环境（推荐，一次解决）：
   ```bat
   cd /d F:\shunyi
   ren .venv .venv_old
   python -m venv .venv
   .venv\Scripts\python.exe -m pip install -r requirements.txt -i https://mirrors.aliyun.com/pypi/simple/
   ```
   下载 Python 时选 **Windows installer (64-bit)**，安装时保持默认勾选的 `tcl/tk and IDLE`。

2. 暂时不改程序，直接编辑配置文件：
   ```
   C:\Users\你的用户名\AppData\Local\BoardTrans\config.json
   ```

### 点「设置…」半天没反应

- **首次打开需要 1~2 秒**（要创建窗口和加载界面），稍等一下。
- 如果一直没反应，看日志：托盘菜单 →「打开日志」，最后几行会说明原因。

### 设置窗口打开了，但界面是空白的

1. 先直接关掉窗口（✕），再从托盘右键 →「设置…」重开一次（第二次通常是好的）
2. 如果还是空白：把系统的显示缩放临时改成 100% 试试
   （设置 → 系统 → 显示 → 缩放），排除高 DPI 缩放导致的渲染问题
3. 还是不行就把日志最后 50 行发出来

### 我改了设置，但按快捷键还是老样子

设置窗口里改完**必须点「保存」**才生效。

- 如果你看到窗口**底部（按钮行上方）**有**黄色提示条**，说明你有未保存的修改，点「保存」即可
- 保存成功会弹 `设置已保存并立即生效，无需重启软件。`

### 设置窗口里显示的档位，和托盘菜单显示的不一样？

正常情况下它们是**同步的**（程序每 0.12 秒比对一次配置）。

- 如果你在窗口里改了档位**还没保存**，窗口显示的是"你正在改的值"，
  底部黄色提示条会明确写出**当前实际生效的值** —— 这是设计如此，不是错乱
- 如果你没有未保存的改动却仍然不一致，退出程序重开一次（多半是旧的窗口线程残留）

### 录制快捷键没反应

- 检查输入框是否还在"请按下快捷键…"状态（可能你点到别处，录制被打断了）→ 重新点「录制」
- 只按修饰键（Ctrl/Alt/Shift）不算完成，要继续按一个主键
- 只按普通键（如单独按 J）会被拒绝，必须带修饰键
- **Win 键组合录不进去**（会被系统优先占用），需要手工改 `config.json` 写 `"hotkey": "windows+j"`

### 保存时提示"这个组合已经被系统或其他软件注册为全局快捷键了"

这是程序**自动检测到了真实冲突**（用 Windows 的 `RegisterHotKey` 探测的）。
原来的快捷键**仍然有效**，换个组合就行，比如 `Ctrl+Alt+J` 或 `Ctrl+Shift+Alt+T`。

### 保存成功了，但按新快捷键没反应

说明这个组合被**用键盘钩子实现的软件**抢占了（输入法、截图工具、游戏加速器等），
这类冲突**无法自动检测**。解决办法：换一个更复杂的组合（`ctrl+shift+alt+` 开头最保险）。

### 下载模型时窗口卡死了吗？

**没有**。下载在后台线程跑，窗口可以正常点按钮、切档位。
只有按钮会短暂变成「取消」，进度条在走，这是正常的。

### 模型下载到哪里了？能改吗？

**默认位置**：**软件所在目录**下的 `models\`（让模型跟着软件走，不再固定写死在 C 盘）。

但有个硬限制：**路径不能含中文**——分词器 sentencepiece 是 C++ 实现，读不了非 ASCII 路径
（实测把模型放到 `F:\键译\models\` 会报 `NOT_FOUND: ...sentencepiece.model: No such file or directory`，
**文件明明存在但它就是读不到**）。所以程序做了自动保护：

| 软件所在目录 | 模型实际存放位置 |
|---|---|
| `D:\BoardTrans\`（纯英文） | `D:\BoardTrans\models\` ✅ 用软件目录 |
| `D:\Program Files\键译\`（含中文） | ⚠️ 自动回退到 `C:\Users\你\AppData\Local\BoardTrans\` |

**怎么知道现在存在哪**：打开设置窗口 →「翻译模型」区块，第一行就写着"模型存放位置：…"，
如果发生了回退，后面还会附一句说明。

**想自定义位置**：编辑 `config.json`（托盘右键 →「打开配置文件」），填：
```json
"models_root": "D:\\BoardTransModels"
```
同样不能含中文，否则会被自动忽略并回退。也可以用环境变量 `SHUNYI_MODELS_DIR` 强制指定。

**升级后原来的模型会丢吗**：不会。程序启动时会自动把旧位置的模型搬到新位置，
搬完还会用托盘气泡告诉你，**不需要重新下载**。

### 提醒太多 / 想彻底关掉提醒

设置窗口 →「翻译模型」区块最下面 →「**通知提醒**」开关。

- **默认开启**：翻译完成、取词失败、快捷键冲突、模型下载完成/失败、启动提示等都会用托盘气泡提醒一次。
- **关闭后**：所有气泡提醒都不再弹出（只记日志，日志在托盘菜单 →「打开日志」）。
  模型下载失败时，设置窗口的模型卡片上会常驻显示失败原因，不会因为关了提醒而看不到错误。
- **改动立即生效，不需要点「保存」**（这个开关是"别再打扰我"，必须一次点击就生效）。
- 另有少数**窗口内的确认框与操作结果框**（删除模型确认、保存成功、放弃修改确认等）不受此开关影响 ——
  它们是你在设置窗口里点击操作的直接反馈，屏蔽掉会让你不知道操作到底成没成。

开关切换后**立即生效**，无需重启；重启后保持你选的状态。手工编辑 `config.json` 里的
`notify_enabled`（`true`/`false`）也会被程序立刻感知，不必重启。

> **请只保留一个键译实例在运行**（任务栏右下角只应看到一个"译"字图标）。
> 同时开两个实例时：两个托盘图标、按快捷键会同时被两边捕获（译文可能被替换两次）、
> 模型目录也可能被互相占用导致删除/下载失败。

### 下载完成后能不能不弹窗？

**现在只弹托盘气泡，不弹模态窗口** —— 不打断你手头的事。若连气泡都不想要，
把上面的「通知提醒」关掉即可。

### 点了「删除」但没删掉

看弹窗提示：

- 提示"模型文件正在被占用" → 先把目标语言切到另一个方向，或退出软件后手工删除该文件夹
- 没有弹窗、点了没反应 → 等两秒（删除时程序会先卸载引擎，需要一点时间）

### ★ 删除模型后，磁盘上还能看到模型文件？

**先确认你看的是哪个位置。** 模型文件可能同时存在于三处，只有前两处归程序管：

| 位置 | 归程序管吗 | 说明 |
|---|---|---|
| `C:\Users\你的用户名\AppData\Local\BoardTrans\packages\<key>\` | ✅ 会删 | 解压后的模型（实际翻译用的） |
| `C:\Users\你的用户名\AppData\Local\BoardTrans\packages_cache\<key>.argosmodel` | ✅ 会删 | 下载的压缩包 |
| 程序所在目录（及其 `models\` 子目录）里的<br>`translate-<key>-*.argosmodel` | ✅ 现在也会删 | 随程序一起放的离线备份 |

> **2026-09-27 修复**：以前只删前两处，程序目录里的离线备份（`translate-zh_en-1_9.argosmodel`
> 这种名字）不在管辖范围内，用户会看到"设置里删了、磁盘上文件还在"。
> 现在删除前会在确认框里**列出所有将被清理的位置**，让用户心里有数。

**删除结果怎么看**（2026-10-01 起删除后不再弹提示框，结果直接看卡片状态）：

- 成功：卡片状态变成 `状态：未下载`，右侧按钮变回 `下载`。
- 部分失败：卡片显示 `状态：删除未完成（部分文件仍被占用）`，右侧出现**「重试删除」**
  按钮，**不会假装成"未下载"**。

如果重试仍失败：退出软件（托盘右键 → 退出）后手动删掉提示里的路径即可。

## 一、模型下载失败

### 现象

- 首次运行卡在"正在下载翻译模型"不动
- 提示 `[X] 模型下载失败: <urlopen error ...>` 或 `timed out`
- 进度条走到一半停住，然后报错

### 为什么会失败

翻译模型从 `https://argos-net.com` 下载（官方源），需要联网一次。
常见原因是公司网络/校园网限制、开了代理但没走代理、或者恰好网络波动。

### 排查与解决（按顺序试）

**第 1 步：确认能不能访问下载源**

用浏览器打开这个地址（它是个 71 MB 的模型包，能开始下载就说明网络没问题）：

```
https://argos-net.com/v1/translate-zh_en-1_9.argosmodel
```

- 能下载 → 网络没问题，跳到第 3 步
- 打不开/一直转圈 → 做第 2 步

**第 2 步：换镜像源**

程序内置了 3 个下载源（官方 + GitHub + 国内加速镜像），会自动依次重试。
如果全都不通，说明是网络环境问题，可以手工下载：

1. 用手机热点/其他网络把这两个文件下下来（用浏览器打开链接即可）：
   - `https://argos-net.com/v1/translate-zh_en-1_9.argosmodel`（71 MB，必需）
   - `https://argos-net.com/v1/translate-en_ja-1_1.argosmodel`（115 MB，只用日文才需要）
2. 把文件放进这个文件夹（没有就自己建）：
   ```
   C:\Users\你的用户名\AppData\Local\BoardTrans\packages_cache\
   ```
   **必须重命名为**：`zh_en.argosmodel` 和 `en_ja.argosmodel`
3. 重新启动程序，它会自动检测到本地模型包并直接解压安装，不再联网

**第 3 步：确认磁盘空间**

模型解压后约 200 MB，加上压缩包约 400 MB。清理一下 C 盘空间再试。

**第 4 步：检查中文路径问题（较少见）**

翻译引擎底层（sentencepiece）**无法读取含中文的路径**。
程序默认把数据放在 `%LOCALAPPDATA%\BoardTrans`，如果**你的 Windows 用户名是中文**，
这个路径就会含中文，导致模型加载失败。

自检工具的第 3 项会检查这一点。如果报"数据目录包含中文"，解决办法：

```bat
setx SHUNYI_DATA_DIR "C:\BoardTransData"
```

执行后**重新打开**程序（环境变量要新开的窗口才生效）。
或者更彻底的办法：新建一个英文名的 Windows 用户账户。

> 本机（开发机）的 Windows 用户名是纯英文，不存在这个问题。

### 下载太慢怎么办

实测速度约 1 MB/s，71 MB 约 1 分钟、115 MB 约 2 分钟。
如果明显更慢，就按第 2 步手工下载（可以用迅雷等工具加速），
把文件丢进 `packages_cache` 文件夹即可。

## 二、快捷键被占用 / 按了没反应

### 现象

- 提示 `快捷键注册失败：「alt+j」无法注册`
- 按 `Alt+J` 完全没反应（连提示都没有）
- 按 `Alt+J` 弹出了别的软件的窗口（比如某个翻译软件）

### 原因

`Alt+J` 是个很常见的组合键，容易被其他软件（输入法、截图工具、翻译软件、
IDE、游戏辅助）抢先用掉。**全局快捷键同一时间只能被一个程序独占。**

### 排查与解决

**第 1 步：确认是不是热点键冲突**

按 `Alt+J`，如果**别的软件有反应**（弹窗、切换、报错），那就是被它占了。做第 2 步。

**第 2 步：换一个不容易冲突的快捷键**

用记事本打开配置文件（托盘菜单 → `打开配置文件`）：

```
C:\Users\你的用户名\AppData\Local\BoardTrans\config.json
```

找到这一行，改成组合更复杂的键：

```json
  "hotkey": "ctrl+alt+j",
```

推荐几个不容易冲突的写法：

```json
  "hotkey": "ctrl+alt+j"        // 首选，几乎不会冲突
  "hotkey": "ctrl+shift+alt+t"
  "hotkey": "f9"                // 单个功能键也可以
  "hotkey": "ctrl+alt+space"
```

保存文件 → **重启程序**（托盘菜单 → 退出 → 重新打开）。

**第 3 步：用自检工具验证**

`0-自检.bat` 的第 7 项会直接告诉你这个键能不能注册：

```
[7/8] 全局快捷键注册
  [正常] 快捷键「alt+j」可以注册
```

如果这一项报异常，就换一个键再试。

**第 4 步：确认程序真的在运行**

看右下角有没有蓝色"译"图标（可能在 `^` 收起区里）。
没有图标说明程序没跑起来，自然按了也没反应。

**第 5 步：确认翻译开关是开着的**

托盘菜单里 `启用翻译` 要打勾。关掉状态下按快捷键会提示"翻译已关闭"。

> 提示：如果程序提示"快捷键注册失败"，它会**继续运行**并且每按一次快捷键都会提醒你，
> 不会静默失效——但你还是应该尽快把快捷键改掉。

## 三、权限不足，取不到词

### 现象

- 按快捷键后提示：`没能取到文字：当前窗口可能不支持自动取词，请先手动选中文字再按快捷键`
- 在某些特定软件里（任务管理器、某些游戏、以管理员身份运行的程序）完全无效
- 在记事本里正常，一到某个软件就不行

### 原因：Windows 的 UIPI 安全机制

Windows 规定：**普通权限的进程不允许向高权限（管理员）进程发送任何输入**。
这是系统级安全限制，不是程序 bug。

所以：
- 你在**普通权限**的软件里打字（记事本、微信、浏览器）→ ✅ 正常
- 你在**管理员权限**的软件里打字（任务管理器、部分安装程序、某些安全软件）→ ❌ 取不到词

### 解决办法

**方案 A（推荐）：让本程序也以管理员身份运行**

- 命令行方式：右键 `1-控制台版.bat` / `2-托盘版.bat` → `以管理员身份运行`
- exe 方式：右键 `键译.exe` → `以管理员身份运行`

这样它就"够得着"高权限窗口了。

> 设置一次永久管理员运行：右键 `键译.exe` → `属性` → `兼容性` → 勾选 `以管理员身份运行此程序` → 确定。
> 之后每次双击都会自动以管理员启动（会弹一次 UAC 授权框，点"是"）。

⚠️ 注意：以管理员运行时，**普通软件里反而可能受影响**（少数情况下管理权限的进程发按键给普通进程会被安全软件更严格地监控）。
如果你主要在普通软件里用（聊天、写文档），**就用普通权限运行，不要开管理员**。

**方案 B：退一步，手动选中再按快捷键**

在取不到词的软件里：**先用鼠标选中要翻译的文字**，再按 `Alt+J`。
程序的取词逻辑第 1 步就是"如果已有选中内容就直接用它"，这条路不受 UIPI 影响。

**方案 C：把取词模式改成只认手动选中**

编辑 `config.json`：

```json
  "capture_mode": "selection",
```

这样程序不再尝试自动选行，只用你手动选中的内容（更可控，但每句都要先选）。

### 还有一种可能：安全软件拦截了"模拟按键"

如果自检工具第 8 项显示：

```
[8/8] 键盘模拟能力（取词/回写的关键）
  [异常] 模拟键盘输入被系统拦截（实际收到 ''）
```

说明是本程序发出的键盘事件被安全软件丢掉了（而不是权限问题），
常见于 360 安全卫士、火绒、企业终端管控软件、某些远程桌面/虚拟机环境。

**解决**：
1. 在该安全软件的"键盘防护""行为拦截""模拟按键防护"设置里，把本程序加进白名单/信任
2. 或者临时退出安全软件测试一下（确认是它的问题后再决定怎么长期处理）
3. 在**远程桌面 / 虚拟机**里运行时，某些环境会禁用模拟输入，这种情况建议在物理机上运行

## 四、其它零散问题

| 现象 | 原因与解决办法 |
|---|---|
| 译文没出现，原文也没了 | 取词成功但回写失败。把 `config.json` 里 `"inject_mode"` 改成 `"type"`（逐字输入，兼容性更好），重启程序 |
| 译文出现两次 | 回写时目标程序自己又粘贴了一次。检查是不是同时开着别的剪贴板增强工具 |
| 剪贴板里原来的内容被替换了 | 默认会还原；若发现没还原，检查 `"restore_clipboard": true` 是否为 true。日志文件里会记录"剪贴板恢复失败" |
| Win+V 剪贴板历史里出现了译文 | 系统行为，程序无法清除。介意就把 `"inject_mode"` 改成 `"type"`（完全不用剪贴板） |
| 翻译结果是空白或乱码 | 看日志。常见原因：模型文件损坏（删掉 `packages\zh_en` 文件夹让它重新下载）；或数据目录被改成中文路径 |
| 程序启动就闪退 | 用命令行运行（见阶段一指南"方式 B"），报错信息会留在窗口里；或看日志 `...\BoardTrans\logs\shunyi.log` 的最后 20 行 |
| 中文→日文翻译质量不太理想 | 这是已知限制：Argos 官方没有中→日直连模型，只能经英文中转，二次翻译会有损失。日常对话够用，正式文本建议人工核对 |

## 七、重复打开出现了多个托盘图标？（2026-09-30 已修）

**原因**：程序原来启动时**没有任何"只能有一个实例"的判定**，每次双击都是一次全新进程，
各自在托盘区挂一个图标；同时第二个还会去抢同一个全局热键（必然失败）并可能重复下载/写配置。

**现在的行为**：启动时先做单实例判定（Windows 命名互斥体 `Local\BoardTrans.SingleInstance`）：

- 若没有实例在跑 → 正常启动，托盘出现一个图标；
- 若已有实例在跑 → 第二个进程**只发一个"请显示设置窗口"的信号就退出**，
  不会创建托盘图标、不注册热键、不碰模型与配置。你会看到已有的设置窗口被唤到前台。

判定用的是 `Local\` 前缀（只在本登录会话内互斥）：多用户/快速切换用户互不干扰，
每个登录会话各有一个托盘图标 —— 这是 Windows 上正确的语义。

**实现位置**：`app/single_instance.py`（命名互斥体 + 命名事件 + 等待线程），
调用点在 `run_stage2.py` 的 `main()` 开头（**必须在创建托盘之前**）。

### 已知残留（不影响托盘与功能，如实说明）

本程序用 PyInstaller **onefile** 打包，双击时实际是「引导父进程 + 应用子进程」两层。
第二个实例的应用子进程会立刻退出（不建托盘图标、不注册热键、不碰配置），但
**引导父进程可能滞留一段时间**（实测 25 秒以上仍存在，等待 0/3/6 秒再退出都无效）。
它没有托盘图标、没有窗口、不占用热键，只在任务管理器里多一行 键译.exe；
它占用的解包临时目录会在**下一次启动时**被自动清理（启动日志里的
「已清理 N 个陈旧的运行时临时目录」）。

曾尝试在第二实例里直接结束这个引导父进程，实测会让第二实例的子进程也不再退出
（比滞留更糟），已回退。若将来要再解决，需要先验证"调用后子进程仍能正常退出"。

如遇异常（例如删掉了互斥体被安全软件拦截），可在设置窗口/托盘里正常使用；
诊断看日志里的这两行：

```
单实例检查：本进程为唯一实例
检测到「键译」已经在运行，正在唤起已存在的窗口…
```

界面是自绘的（圆角卡片、按钮、开关都是程序画的），"发虚"来自下面几处，均已修复：

## 九、设置窗口卡顿 / 点不动（2026-09-29 已修）

设置窗口跑在独立线程里，它与程序其它部分的通信都通过一个"指令队列"。
下面三类问题都曾导致界面反应慢甚至像死掉，现已修复并加了自动化回归
（`tools/test_ui_responsive.py`，11 项全通过）：

| 曾经的成因 | 表现 | 现在的做法 |
|---|---|---|
| 自绘卡片/开关**空闲时反复全量重画**（实测每秒上百次） | CPU 占用偏高、输入发涩、偶尔闪烁 | 只在**尺寸或配色变化**时重画；自检 250ms 一次、稳定后退避到 1 秒 |
| 心跳**每 120ms 才轮询一次、且一次把队列排空** | 命令响应固定延迟 ~125ms；指令一多界面就"未响应" | 轮询间隔降到 **50ms**；每轮**最多处理 20 条**指令，剩下的下轮立刻接着做，事件循环始终有机会响应输入 |
| 别的线程**直接操作界面控件**（tkinter 不是线程安全的） | 界面挂起、窗口变白、进程静默中断 | 统一走 `设置窗口.run_in_ui(...)`；脚本序列中跨线程调用实测 **0 次** |
| 滚轮用**进程级全局绑定** | 可能影响同进程其它窗口/控件的滚轮 | 改为**逐控件绑定**，作用域清晰、无残留 |
| 窗口线程启动**最长等 8 秒** | 点「设置…」后长时间无反应 | 等待上限降到 **3 秒**，超时会写日志 |

如果你自己写脚本操作设置窗口，请遵守一条规则：
**不要在别的线程里碰 Tk 对象**（哪怕是 `winfo_width()` 这种只读调用），
一律用 `settings.run_in_ui(函数)`，它会安全地在窗口线程里执行并返回结果。

日志里出现下面这行，说明 UI 线程里有一段耗时操作，是排查卡顿的入口：

```
[WARNING] 设置窗口单轮心跳耗时 XXX ms（处理 N 条指令）：若持续出现，说明 UI 线程里有耗时操作需要挪走
```

### 首次打开要等半秒？（2026-10-01 已修）

**现象**：程序刚启动后第一次点「设置」，窗口要顿一下才出现；之后再打开就很快。

**原因**：设置窗口是**懒加载**的 —— 第一次点「设置」时才现启动窗口线程、创建 Tk、
构建整个界面（含 31 张文字超采样图、20 多个自绘组件底图，以及多行文本的"影子排版"）。
实测：首次 `open()` 到界面就绪 **270~330ms**，第二次只要 **30~70ms**（只等一次心跳把
窗口显示出来）。这两百多毫秒全落在你的等待里，就是"卡一下"的手感。

**修法**：程序启动后在**后台提前把界面建好**（窗口保持隐藏、不抢焦点），启动路径本身
不被阻塞。你第一次点「设置」时只剩"显示"这一步：

| | 无预热 | 后台预热后 |
|---|---|---|
| 首次点「设置」→ 窗口出现 | 270~330 ms | **55~65 ms**（与第二次打开一致） |
| 预热开销 | — | 启动后约 1 秒在后台跑完，无感 |

顺带修掉两个相关的观感问题：

- 构建期间 Tk 根窗口默认是**可见**的，屏幕上会先闪一个空白/半成品窗口 → 改为创建后立刻隐藏；
- 显示窗口时先做模型状态的磁盘检查（列目录、算占用），会把"窗口出现"拖慢
  → 改成等窗口画出来、事件循环空下来再刷新。

**正常启动后，日志里「服务已启动」之后约 1 秒应该出现这两行**，那就是预热完成的标志：

```
[INFO] 设置窗口 ttk 主题: clam（字体: Microsoft YaHei UI）
[INFO] 界面渲染模式: 超采样 3× 降采样（抗锯齿）
```

若出现「设置窗口预热失败」，说明预热线程里出了异常（不影响使用，只是首次打开会退回到
"现建界面"，也就是原来那样慢一下），日志里有完整堆栈可查。

回归：`tools/test_prewarm.py`（13 项：预热是后台行为 / 窗口保持隐藏 / 幂等与并发安全 /
首次打开提速 / 文字控件值没变不重渲染）。
