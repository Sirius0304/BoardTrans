# 键译 · 技术方案说明

> 一句话：在任意软件里用中文打字，按 `Alt+J`，刚才那句话原地变成英文或日文。全程离线，不联网翻译。

---

## 一、技术栈

| 层面 | 选型 | 说明 |
|---|---|---|
| 语言 | Python 3.13（64 位） | 匹配用户机器现有环境，实测全部依赖均有官方 wheel |
| 翻译推理 | **CTranslate2 4.8.2** | 专为 CPU 优化的 Transformer 推理引擎，支持 int8 量化，速度是原生 PyTorch 的 3～5 倍 |
| 分词 | **SentencePiece** | 模型自带分词器，无需额外下载 |
| 模型 | **OPUS-MT**（Marian 架构） | 赫尔辛基大学开源，中→英为 74M 参数模型；通过 Argos Translate 官方索引分发 |
| 全局热键 | **keyboard** | Windows 底层键盘钩子，可全局监听并拦截组合键 |
| 托盘界面 | **pystray + Pillow** | 图标用 Pillow 现场绘制，不依赖外部图片文件 |
| 剪贴板 | **pyperclip + ctypes(SendInput)** | 两种回写方式，见下文 |
| 打包 | **PyInstaller 6.22（onefile）** | 单文件 exe，双击即用，无需装 Python |

**为什么不用 argostranslate 这个现成库？**
它的依赖链会经 stanza 拉入 PyTorch（安装体积 2 GB+）。而 `.argosmodel` 包本身就是一个 zip，
里面是标准的 CTranslate2 模型目录 + `sentencepiece.model`，直接用 CTranslate2 加载即可。
改成直接加载后，**运行时依赖体积从 GB 级降到约 60 MB**，打包出的 exe 也从几百 MB 降到约 50 MB。

## 二、取词方案（为什么这么选）

需求给了两个候选方案，实测后采用**两者结合的混合方案**：

```
按下 Alt+J
   ├─ 第 1 步：直接发 Ctrl+C
   │     └─ 剪贴板有新内容？ → 说明用户已手动选中文字，直接用它（语义最准）
   └─ 第 2 步：拿不到就发 Shift+Home 选中光标以前的整行，再 Ctrl+C
         └─ 仍然拿不到 → 提示"请先手动选中文字再按快捷键"
最后：统一按 Delete 删掉选中内容，光标留在原位等译文
```

**为什么不只用方案 A（先选中再按快捷键）**：会打断"打字即翻译"的流畅感，
每句话都要多一个"先选中"的动作，日常聊天时很别扭。

**为什么不只用方案 B（自动回删选行）**：不同控件对"整行选中"的边界处理不一致，
在聊天窗口、地址栏、代码编辑器里表现各异；而且用户如果已经手动选好了要翻译的内容，
自动选行反而会覆盖掉用户的意图。

混合方案兼顾两者：**有选中就用选中，没选中就自动选行**。
取词全程有超时保护（单次 0.6 秒），任何一步失败都返回明确的失败原因，绝不卡死。

## 三、翻译引擎选型对比（都是实测数据）

| 方案 | 体积 | 中文→英文 | 中文→日文 | 结论 |
|---|---|---|---|---|
| **OPUS-MT 小模型（本项目采用）** | 71 MB + 115 MB | 24 句/秒，质量好 | 经英文中转，质量可用 | ✅ 采用 |
| NLLB-200-distilled-600M | ~600 MB | 质量更好 | 质量更好 | ❌ 体积大 3 倍、下载源（HuggingFace）国内需镜像，风险高 |
| opus-mt-tc-big-zh-ja 直连大模型 | ~405 MB | — | 理论上最好 | ❌ 官方只有 PyTorch 版；社区的 CTranslate2 转换版实测词表与模型不匹配、输出乱码，不可用 |

**关于中→日**：Argos 官方索引里没有中→日直连包（只有 `zh→en`、`en→zh`、`en→ja`），
所以日文方向采用官方的**中转方案**：先译成英文，再译成日文。
代价是质量会有一定损失（详见下方实测样例），好处是下载体积最小、来源最可靠。

> 实测中还发现一个重要细节：`en→ja` 模型在 `beam_size=1` 时会严重错译
> （`Hello, nice day.` → `昨日は、お昼の夜を過ごして、`），`beam≥2` 才正常。
> 因此代码里给日文方向设了 `beam` 下限保护（`JA_MIN_BEAM = 3`）。

## 四、两种质量档位的具体差别

两档使用**同一套模型，通过解码策略区分**——因为再引入一个大模型会让下载体积翻 3 倍以上，
而我们实测后发现"小模型 + 精细解码"已经能满足日常需求。

| | 高速度（默认） | 高质量 |
|---|---|---|
| 解码方式 | 贪心解码 `beam_size=1` | 束搜索 `beam_size=8` + 长度惩罚 1.1 |
| 中文→英文 实测耗时 | **平均 26 ms/句** | **平均 54 ms/句** |
| 中文→日文 实测耗时 | 平均 87 ms/句（beam=1/3） | 平均 109 ms/句（beam=8/8） |
| 长文本（3 句） | 0.15 s | 0.33 s |
| 质量差异实例① | `这个功能已经开发完了…` → `This is already developed, but…` | → `It's been developed, but…`（更地道） |
| 质量差异实例② | `…重视跨文化沟通能力…` → `…focusing on intercultural communication capabilities…` | → `…have begun to focus on cross-cultural communication…`（更准确） |

> 说明：高质量档是通过"让模型多算几条候选路径再挑最好的"来提升质量的，
> 所以耗时约为高速度档的 2 倍多，但绝对值仍在 0.1 秒量级，日常使用几乎感觉不到延迟。

## 五、回写方式与剪贴板取舍

| 方式 | 原理 | 优点 | 取舍 |
|---|---|---|---|
| `paste`（默认） | 备份剪贴板 → 写入译文 → Ctrl+V → **恢复原剪贴板** | 瞬间完成，兼容所有输入框 | Windows 的"剪贴板历史（Win+V）"仍会留下一次译文记录；如果原来剪贴板里是图片/文件（非文字），恢复时无法还原（程序会在日志里记录） |
| `type` | 用 SendInput 逐字符发送 Unicode | **完全不碰剪贴板**，连剪贴板历史都不会污染 | 速度略慢；个别应用的自动补全可能对逐字符输入有反应 |

两种方式都可在 `config.json` 里一行切换（`"inject_mode": "paste"` 或 `"type"`）。

## 七、稳定性设计（针对需求的几条硬要求）

| 需求 | 实现方式 |
|---|---|
| 钩子不能因单个应用异常而崩溃 | 热键回调只做入队（微秒级返回），真正的处理在独立工作线程；全流程 `try/except` 兜底，异常写日志并弹托盘提示 |
| 权限不足窗口要降级提示而非闪退 | 取词失败时区分原因提示："没能取到文字：当前窗口可能不支持自动取词…"；自检工具会明确指出"目标窗口是管理员权限"这一常见原因 |
| 状态记忆必须落盘 | 配置每次变更都执行"写临时文件 → `fsync` → `os.replace` 原子替换"，进程被强杀或直接关机都不会写坏配置 |
| 启动不能慢 | 模型加载实测 0.12 秒；引擎懒加载 + 启动后后台预加载 |
| 性能陷阱 | 已修复：数据目录探测函数原本每次调用都要写删一个探针文件（在开启实时防护的 Windows 上单次要 110 ms），改为只探测一次并缓存，使中→日耗时从 147 ms 降到 36 ms |
| 删了原文就不能白删（2026-10-18） | 取词成功 = 原文已被 `Delete` 删掉。此后**任何**不产出译文的退出路径都必须把原文还回去：模型缺失的检查提前到取词**之前**（不取词自然不删字）；翻译结果为空、翻译抛异常、回写失败统一走 `service._restore_original()` 回注原文，连回注都失败时把内容留在剪贴板并提示手动粘贴 |
| 模型包坏了要能自愈（2026-10-18） | 缓存只认"字节数完全一致"（zip 中央目录在尾部，99% 的包必然是坏包，旧实现还顺带把断点续传短路了）；解压遇 `BadZipFile` 自动删包重下一次，第二次仍坏才报错 |
| 回写结果可感知（2026-10-18） | `inject_text` 返回 `(是否可能成功, 方式说明)`；`type` 模式的布尔值来自 `SendInput` 真实回执，`paste` 模式只能保证"剪贴板已写 + Ctrl+V 已发"（Windows 无粘贴回执）。失败时提示文案如实说明，并把译文留在剪贴板供手动粘贴 |

## 八、已知限制（如实说明）

1. **中→日质量弱于中→英**：因为要经英文中转。日常对话够用，正式书面文本建议核对。
2. **管理员权限窗口**：本程序不是管理员运行时，无法向以管理员身份运行的窗口（如任务管理器）发送按键。解决办法：右键本程序"以管理员身份运行"。
3. **剪贴板历史**：`paste` 模式下译文会进 Win+V 历史（系统行为，无法程序化清除）。介意就用 `type` 模式。
4. **自动取词取「整段」，且一键完成**（2026-10-12 起取整段，2026-10-16 改为一键）：
   先试你已经选中的内容；没有选中，就自动取「光标所在整段」——
   `Shift+Home` 选到本行行首，再一次 **`Ctrl+Shift+Up` 直接扩到段首**（Windows
   编辑控件的标准行为），整段一次到手，只复制 2 次（旧实现逐行 `Shift+Up`
   试探，10 行段落要复制 10 次、多花约 0.7 秒）。
   若目标程序不认 `Ctrl+Shift+Up`（个别自绘控件），自动退回逐行扩展，
   每扩一行复制一次、以空行开头即判定越界并退一行 —— 不会误吞上一段。
   旧实现只取到行首，多行长文本于是只剩最后一行，这就是「只翻译了最后一段」的成因。
   兜底路径上限 25 行以免误吞整篇文档；想只翻一句，可把 `capture_mode` 设为 `line`。
5. **按键后立刻开始选字（2026-10-16 提速）**：第一步"你有没有选中文字"的判定
   原来是等剪贴板变化、超时 1.2s 且重试一次 —— 而"没选中"恰恰是常态，于是每次
   按键都要白等约 2.7 秒。现在改为**短探测**：记下剪贴板序列号
   （`GetClipboardSequenceNumber`，读取零成本、不用打开剪贴板），150ms 内没有
   内容写入就判定"未选中"，立刻转入自动取段。真正有选区时复制通常 10~60ms 完成，
   精确性不受影响；超慢应用可用 `selection_probe_ms` 调大（≥600 自动恢复保守策略）。
   实测（`tools/diag_capture_latency.py`，假控件但真实等待时序）：无选区场景
   **2940ms → 356ms**，有选区场景 83ms → 84ms（无差异）。
6. **模型预热与取词并行（2026-10-16 提速方案②）**：按键后立刻在后台线程把当前
   目标语言的模型读进内存（`engine.ensure_loaded`），与取词那 0.3~0.4 秒重叠；
   过去是"取完词再加载模型再翻译"的串行结构，模型被空闲释放后（或进程内首次
   翻译）用户会看到"字选完了还不动"。已经加载时 `is_ready_for` 直接返回，
   不惊动线程；加载失败不影响翻译（翻译时仍会自行加载）。
   实测（`tools/diag_warmup.py`，真模型）：按键→模型就绪 串行 **0.47s** →
   并行 **0.11s**（落在取词窗口内，翻译阶段省 0.36s；冷启动省得更多）。
7. **粘贴确认等待按前台窗口自适应（2026-10-16 提速方案④）**：粘贴后要等目标程序
   真正读走剪贴板才能还原它。游戏（全屏）在帧循环里异步读剪贴板，实测 0.15s 不够
   （会贴出旧剪贴板，2026-10-14 报障），所以给 0.8s；而普通桌面程序 16ms 内就粘贴
   完毕，等 0.8s 纯属浪费。现在由 `_foreground_is_fullscreen()`（前台窗口是否铺满
   所在显示器）自动二选一：桌面 0.25s / 全屏 0.8s。判定异常或取不到时退化为
   桌面快路径（最长也只等 0.25s，且有"粘贴失败回注原文"兜底）。
   实测（`tools/test_game_paste.py` 真实计时）：整条回写 桌面 **401ms** /
   全屏 **951ms**，桌面场景每次省约 **0.55s**。
